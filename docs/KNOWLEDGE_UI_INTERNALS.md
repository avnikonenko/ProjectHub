# Knowledge interface internals

Contributor reference. For everyday use, see [Overview and Knowledge](PROJECT_KNOWLEDGE_UI.md).

## API and implementation

- `GET /api/projects/{id}/codex/knowledge`: published snapshot plus current evidence
  availability and current coverage. No model call.
- `POST /api/projects/{id}/codex/knowledge/brief`: confirmed requests
  atomically save validated Knowledge and its summary. The compatibility field
  `publish` cannot disable saving. Optional `generate_scheme:true` requests a
  server-side Scheme follow-up after success. The legacy generation alias
  `POST /api/projects/{id}/codex/analysis/preview` also saves automatically.
- `POST /api/projects/{id}/codex/knowledge/preview/publish`: activate a legacy saved
  preview by publication ID without generation; return 409 for stale/conflicting results.
- `GET /api/projects/{id}/codex/knowledge/preview`: last earlier
  legacy preview record, or null. Read-only and project-scoped; no model call.
- `GET /api/projects/{id}/codex/generation/status?kind=knowledge`: generation progress.
- Existing conversation/transcript hash resolvers open original evidence.

Publication pairing rejects missing, empty or whitespace publication IDs when
calculating `paired_with_current_brief`. This field remains truthful for legacy
paired results; a new Knowledge Summary is paired with its Knowledge snapshot,
not the general Overview. Its optional `snapshot.summary` must match the snapshot's
publication ID. General Overview refresh uses `/codex/brief`, with independent
`brief` progress/cancellation; Knowledge uses `knowledge` progress. Each uses its
own project/view generation lease. Other project views may generate concurrently.
Knowledge generation starts on request and saves successful results automatically.

project/publication appearing under the current project.


### Overview highlights and navigation

A legacy Overview generated by the knowledge pipeline shows **Important choices** only
when its publication and project match the retrieved snapshot. The deterministic
selection uses supported, nonsuperseded, nonconflicting AGREED records first, then
up to two UNRESOLVED records, with a total limit of five. Stable item IDs break
ties; this does not claim scientific importance or cross-session chronology.
Exact repeated statements with identical scope/status are suppressed in highlights
only. The Knowledge page retains all records.

Choice links use `#knowledge?project=ID&publication=PUBLICATION&item=ITEM_ID`.
A publication mismatch blocks substitution and offers an explicit current-snapshot
view. Missing item IDs are reported. Historical knowledge is not silently replaced
with the latest snapshot, and unrelated knowledge is never attached to legacy briefs.
An unavailable project link displays an error rather than another project's data.

When Overview is replaced or a backing revision is deleted, the old paired summary
is copied into the Knowledge snapshot in the same transaction. Its publication ID
and tags are preserved.

Matching direct-user choices supported by the same exact passage can appear under
**Interpretations from the same passage**. This display grouping preserves each
record, status, evidence and filter count. Numbered proposal acceptances, distinct
scopes, and conflicting or stale records remain separate. Direct links reveal
related records. Context-review notes are separate from historical design status.

## Remaining limits

- Interface tests cover display and navigation; extraction accuracy needs separate evaluation.
- Knowledge dropdowns use exact status and category values. The scope field
  matches a substring and offers recorded scope suggestions. Project-wide search
  is separate and provides no semantic retrieval or scope equivalence inference.
- The Knowledge tab browses the current saved snapshot. **Earlier saved versions**
  shows the latest legacy preview when available. Regular Knowledge revisions are
  accessible through the revisions API. Historical item links report publication
  mismatches.
- Failed or cancelled generation preserves saved Knowledge and successful extraction caches; only a complete validated result replaces normal saved Knowledge. Earlier previews retain their separate storage.
- Source navigation depends on stored descriptors and current availability. Saved
  excerpts remain accessible when original navigation cannot be offered.

Use an isolated data directory and port for development as described in
[the pipeline guide](KNOWLEDGE_PIPELINE.md#isolated-testing).

## Implementation Choices & Limits validation

Validation of the earlier declaration-only version on 2026-11-17 used an isolated, frozen ProjectHub checkout and real
Codex (`gpt-6.1-sol`, medium reasoning). One request completed in 204.5 seconds:
100 selected declarations retained their inspected defaults, with 96 purposes,
41 trade-offs and one documented rationale; unsupported explanations stayed
unknown. Reported usage was 56,261 input and 9,925 output tokens. This is one
measured run, not a general speed or cost guarantee. Coverage explicitly recorded
103 omitted declarations, unsupported-language files and partial reads.

An isolated Firefox check verified saved values, conditional/expression/required
labels, local search, and source-change warnings without automatic regeneration
or model calls. Automated checks cover project ownership, independent revisions,
source changes, cancellation/failures and explanation-reference validation.

The revised choices view was evaluated with real Codex (`gpt-6.1-sol`, medium)
against an isolated Python repository containing a 24-file cap imported from
another module, a 12-record slice, a `.bak` exclusion, an exception fallback and
an unsupported export. All five behaviors were surfaced with usage references;
an unused worker default stayed a parameter-only record. One request completed
in 34.4 seconds (16,801 input / 1,430 output tokens). This fixture demonstrates
the supported paths, not exhaustive repository analysis. Static inspection of
ProjectHub completed its 63 supported files within the unchanged five-second
budget; selection and evidence-size limits still make the result partial.

## Topic metadata

The explicit `/codex/tags` action updates only the selected saved result’s tag
metadata, using publication ID or Q&A generation timestamp plus atomic freshness
checks. Main Knowledge and Q&A generation never invokes tagging. Tag generation
uses project/configuration-scoped caches and bounded batches,
separate from extraction caches and Overview selection. Unchanged memberships
can be reused; successful batch caches survive later failures. Memberships are
validated against existing record IDs. Q&A deletion prunes current memberships
while preserving historical revisions. The project taxonomy is bounded to 400 topics, with up to 40 new topics per reply;
excess topics cause explicit failure rather than silent assignment truncation.

### Optimized tag generation (default)

Large saved results use a shared topic catalog, compact numeric inputs, and packed
output rows: each row starts with the record ID followed by zero to four topic IDs.
The parser requires every record exactly once and rejects foreign or duplicate IDs.
Tag-only threads use a short classification base instruction; project instructions,
read-only execution, denied tool approvals and strict source isolation remain.
Ordinary Overview and Q&A generation are unchanged.

Assignment batches contain up to 600 records or roughly 100,000 compact characters,
with a separate 240,000-character check on the actual full prompt. The existing
worker setting is respected. Small results that fit one legacy batch keep a single
combined catalog-and-assignment call. Set `PROJECTHUB_COMPACT_TAGS=0` and restart to
use the older strategy. No reasoning effort is lowered automatically.

An isolated complete cold run on 3,162 records at medium reasoning with the saved
eight-worker setting took **122.42 seconds**, ten model calls, and **252,473 reported
tokens**. It produced 15 topics and tagged 3,130 records; all 32 untagged records
remain accessible. Original records and source bytes were unchanged. An unchanged
repeat took **0.238 seconds with zero model calls**.

For comparison, cold four-worker observations were 299.20 seconds / 469,900 tokens
before the context optimization; 261.06 seconds / 358,648 tokens with classification
context; and 293.50 seconds / 271,009 tokens with larger batches but verbose output.
These are individual runs, with differing worker counts in the final run, not a
controlled attribution of every improvement or a universal timing guarantee.
A grouped-by-topic output experiment was rejected after strict coverage validation
caught omitted/conflicting record IDs; that format is not used.

All nine previously selected requirement cases received tags. Independent review
found some broad/weak assignments and material requirements among the untagged
records. Assigned percentage is not semantic accuracy or proof of complete recall.
Users retain All items, Untagged, original evidence, and the ability to inspect tags
as AI interpretations. Generation stays explicit and preserves the previous result
on failure or cancellation.

Negative tag assignments also track their topic catalog. When new subjects become
available, previously untagged records are checked against that catalog without
reclassifying already-tagged records. Older snapshots without this marker may
require one negative-only recheck. Unchanged catalogs and records remain eligible
for zero-call reuse. Transient progress-read errors clear when polling recovers;
actual generation errors are retained.
